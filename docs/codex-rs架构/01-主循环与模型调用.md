# Codex Rust: 主循环与模型调用

这一层回答两个问题：

- Codex Rust 一次 turn 是怎么跑起来的
- 模型请求是怎么从 `core` 内部状态编译出来的

## 1. 文件拆分

- `core/src/codex.rs`
- `core/src/codex_thread.rs`
- `core/src/tasks/regular.rs`
- `core/src/client_common.rs`
- `codex-api/src/`
- `core/src/client.rs`
- `core/src/default_client.rs`

## 2. 入口关系

在 `codex-rs` 里：

- `cli/` 只是多命令入口
- `tui/` 和 `tui2/` 是交互前端
- 真正的核心循环在 `core/src/codex.rs`

`RegularTask` 本身很薄，核心只是：

- `tasks::RegularTask::run(...)`
- 调 `codex::run_turn(...)`

所以真正的 agent 主循环还是在 `core`，不是在 TUI 层。

## 3. `Codex` / `CodexThread` 的角色

从 `core/src/codex.rs` 和 `core/src/codex_thread.rs` 看：

- `Codex`
  是高层系统接口，内部是 submission queue + event queue
- `CodexThread`
  是线程/会话的双向通道封装

这意味着它的核心抽象不是“REPL screen”，而是：

- 提交 `Op`
- 消费 `Event`

这种接口天然更适合作为库给多个前端复用。

## 4. Prompt 是怎么构造的

`core/src/client_common.rs` 里的 `Prompt` 结构很关键，主要字段是：

- `input: Vec<ResponseItem>`
- `tools: Vec<ToolSpec>`
- `parallel_tool_calls`
- `base_instructions_override`
- `output_schema`

它和 Claude Code 最大的区别之一是：

- Claude Code 更像动态拼 `system + messages + attachments + tools`
- Codex Rust 更像明确构建一个 `Prompt` 值对象，然后交给 client / API 层

## 5. model client 的边界

从 `core/src/client_common.rs` 和 `codex-api/src/` 看，模型适配层主要职责是：

- 承接 `Prompt`
- 处理流式 `ResponseEvent`
- 适配 Responses / Chat / SSE / websocket 等不同 wire API

这里的好处是边界比较干净：

- `Prompt` 是 core 里的统一请求抽象
- `codex-api` 负责对接具体模型 API

## 6. 和 Claude Code 的主要区别

### 6.1 相同点

- 都有中心主循环
- 都要在模型调用前构建历史、工具和额外上下文
- 都要把 tool result 再并回下一轮

### 6.2 不同点

- Claude Code 的编排感更强，很多步骤在 `query.ts` 直接串起来
- Codex Rust 把主循环、Prompt、client、task 分成了更明显的层
- `CodexThread` 这种双向接口更像库式设计，不像单纯 REPL app

## 7. 一句话总结

Codex Rust 在这一层的特点是：

- 主循环仍然集中
- 但输入输出边界比 Claude Code 更明确
- 更容易把同一套核心逻辑挂到 TUI、headless exec、MCP server 等不同前端上
