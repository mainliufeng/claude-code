# Codex Rust: 真实调用链与关键耦合点

这一份不再按模块概念讲，而是按真实代码路径讲。

## 1. 一次 regular task 的真实主链

最短主链是：

1. `tasks::RegularTask::run(...)`
2. `codex::run_turn(...)`
3. 从 `SessionState.history` 取上下文
4. 构建 `Prompt`
5. 调 model client
6. 流式拿 `ResponseEvent`
7. 解析成普通输出或 tool call
8. `ToolRouter::build_tool_call(...)`
9. `ToolRouter::dispatch_tool_call(...)`
10. `ToolOrchestrator::run(...)`
11. tool runtime 真执行
12. `FunctionCallOutput / CustomToolCallOutput` 回到 history
13. 必要时 compact / truncate
14. 继续下一轮

## 2. 历史规范化发生在 `ContextManager`

`ContextManager::for_prompt()` 在发模型前会做：

- `normalize_history()`
- 去掉不适合发给模型的 item

而 `normalize_history()` 至少保证两件事：

- every call has output
- every output has call

这和 Claude Code 的 `normalizeMessagesForAPI` 很像，但落点不同：

- Claude Code 是消息发送前的 normalize
- Codex Rust 是 `ContextManager` 自身的历史规范化

## 3. skill 注入链

Codex Rust 的 skill 注入更直接：

1. user input 明确提到 skill
2. `build_skill_injections(...)`
3. 读取 skill 文件
4. 转成 `SkillInstructions`
5. 再转成 `ResponseItem::Message`
6. 直接进入 prompt input

和 Claude Code 相比，它少了一层：

- `skill_listing / skill_discovery` 这种常驻 attachment 引导层

## 4. compact 链

Codex Rust 的 compact 更接近：

- 运行一个 compact task
- 模型生成 compact summary
- 重建 compacted history
- `replace_history(...)`

而不是像 Claude Code 那样：

- tool result budget
- microcompact
- full compact
- invoked skill restore

这说明 Codex Rust 的 compact 粒度更粗，但历史结构更统一。

## 5. 最重的几个耦合点

### 5.1 `Prompt` 和 `ContextManager`

`Prompt.input` 直接来自 session history，所以历史管理和模型请求构造天然强耦合。

### 5.2 `ToolRouter` 和协议消息

工具调用不是业务层自定义对象，而是直接从 `ResponseItem` 解析，所以 tool routing 和协议层强耦合。

### 5.3 `ToolOrchestrator` 和 sandbox/approval

approval、sandbox、retry 是放在同一条执行管线里的，这让工具执行边界更清晰，但也让它和执行策略绑定很深。

### 5.4 `skills` 和 `user instructions`

skill / AGENTS.md instructions 都是通过“特殊 user message”注入，这让上下文体系更统一，但也意味着它们和 prompt 历史是重耦合的。

## 6. 一句话总结

如果用一句话概括 Codex Rust 的真实结构：

- 它是一个以 `ContextManager + Prompt + ToolRouter/ToolOrchestrator + SessionTask` 为骨架的核心库式 agent runtime
