# 真实调用链与关键耦合点

前面几份文档主要按模块讲职责；这一份改成“按真实代码路径讲系统”。

重点回答：

- 一轮里真正先后发生了什么
- 哪些函数是关键交汇点
- 为什么某些模块虽然概念上可分，但运行时还是重耦合

## 1. 主循环的真实顺序

`src/query.ts` 里，一轮的主链可以概括成：

1. `getMessagesAfterCompactBoundary(messages)`
   先取 compact boundary 之后真正参与当前轮的消息
2. `applyToolResultBudget(...)`
   对大 tool result 先做预算控制
3. `snipCompactIfNeeded(...)`
   feature 打开时做 snip
4. `deps.microcompact(...)`
   优先收缩旧工具结果
5. `contextCollapse.applyCollapsesIfNeeded(...)`
   feature 打开时做 collapsed view 投影
6. `deps.autocompact(...)`
   判断是否进入 full compact / summarize
7. 收集 attachment，并生成 meta messages
8. 组装 `system + messages + tools`
9. 调模型
10. 如果返回 `tool_use`，进入工具执行链
11. 把 `tool_result` 并回历史，再递归下一轮

这条顺序本身已经说明：

- compact 发生在模型调用前
- 但 compact 的输入高度依赖上一轮工具执行结果

## 2. 模型请求是怎么组出来的

`src/services/api/claude.ts` 里，请求构造的关键点有这些：

1. `isToolSearchEnabled(...)`
   判断本轮是否启用 tool search
2. `extractDiscoveredToolNames(messages)`
   从消息历史里提取已经 discover 的 deferred tools
3. 基于 `useToolSearch` 和 discover 结果生成 `filteredTools`
4. `toolToAPISchema(...)`
   把具体工具转成 API `tools[]`
5. `normalizeMessagesForAPI(messages, filteredTools)`
   把内部消息规范化成模型 API 可接受的消息数组

这里一个很关键的实现细节是：

- tool 不是“注册完就全部发给模型”
- 真正发给模型的是 `filteredTools`
- 而 `filteredTools` 又受历史消息里的 discover 状态影响

所以模型输入并不是静态配置，而是和历史消息互相影响的。

## 3. attachment 是怎么真正进入消息历史的

`src/utils/attachments.ts` 里：

- `getAttachments(...)`
  负责收集所有当前轮需要的 attachment
- `createAttachmentMessages(...)`
  会遍历 attachment，并通过 `createAttachmentMessage(...)` 产出实际消息

也就是说，attachment 并不是“辅助对象”，它最终会变成真实消息块，进入模型上下文。

## 4. tools 不只是执行，还会主动产出 attachment

`src/services/tools/toolExecution.ts` 里能看到，工具执行过程中除了普通 `tool_result` 外，还会主动产出 attachment message，例如：

- `hook_permission_decision`
  权限 hook 自动允许/拒绝后，会插入一条 attachment message
- `structured_output`
  如果工具产出结构化输出，会额外存成 attachment message
- `hook_stopped_continuation`
  hook 阻止继续执行时，也会插入 attachment message
- `result.newMessages`
  工具本身还可以直接返回新的消息，这些消息会被并回会话

这说明：

- 工具执行层并不是只返回一个 `tool_result` 字符串
- 它可以直接修改会话里后续可见的消息形态

这是工具层和上下文层的第二个重要耦合点。

## 5. SkillTool 是最典型的跨模块实现

`src/tools/SkillTool/SkillTool.ts` 里，真正执行 skill 时会做三件事：

1. 读取并处理 skill 内容
2. `addInvokedSkill(...)`
   把 skill 写进全局 invoked skill 状态，供 compact 后恢复
3. 通过 `createUserMessage({ isMeta: true })`
   把 skill 正文直接注入会话消息

所以 SkillTool 的完整角色是：

- 工具系统里的一个 tool
- 上下文系统里的一个内容注入器
- compact 恢复系统里的一个状态写入方

这也是为什么前面不能把 tool 和 context 简化成两块独立层。

## 6. conversation recovery 不只是恢复 transcript

`src/utils/conversationRecovery.ts` 里有一个很重要的恢复逻辑：

- `restoreSkillStateFromMessages(messages)`

它会在恢复消息时：

1. 扫描 `invoked_skills` attachment
2. 对每个 skill 再次调用 `addInvokedSkill(...)`
3. 如果发现已有 `skill_listing`，则调用 `suppressNextSkillListing()`

这意味着恢复会话时恢复的不只是“消息文本”，还包括：

- compact 之后需要继续保住的 skill 状态
- 进程级的 skill listing 抑制状态

所以 resume 不是单纯把 transcript 读回来，而是要重建一部分运行时内存状态。

## 7. `normalizeMessagesForAPI` 不是简单格式转换

`src/utils/messages.ts` 里的 `normalizeMessagesForAPI(...)` 实际做了很多“修复型”工作，例如：

- 合并消息
- 修复 resume 后可能遗留的 orphaned tool result
- 去重工具调用块
- 防止消息顺序触发 API 约束错误

这说明消息标准化层不是薄薄一层 serializer，而是一个“会话修复层”。

也正因为如此：

- resume
- tool result
- attachment
- compact

最终都会在这里交汇。

## 8. session memory 和 extract memories 不是一回事

这两个功能很容易混在一起，但代码里其实是两条不同链：

### 8.1 Session Memory

核心文件：

- `src/services/SessionMemory/sessionMemory.ts`

它的特点是：

- 先根据 token 数、tool call 数、最近一轮是否还在大量调用工具来判断是否该触发
- `setupSessionMemoryFile(...)` 会创建/读取 session memory 文件
- 它直接复用 `FileReadTool.call(...)` 读 memory 文件内容

也就是说，session memory 更像：

- 当前会话内的一份持续更新记忆文件

### 8.2 Extract Memories

核心文件：

- `src/services/extractMemories/extractMemories.ts`

它的特点是：

- 会构造 memory manifest
- 用 `runForkedAgent(...)` 启一个 forked subagent 去提取记忆
- 明确设置 `skipTranscript: true`
  避免 memory 提取过程污染主 transcript、引发 race condition
- 最终根据写入路径回收结果

也就是说，extract memories 更像：

- 异步的、偏后台的记忆提炼流程

## 9. `ToolUseContext` 是真正的跨层共享对象

从调用链看，`ToolUseContext` 会一路流经：

- query
- attachments
- toolExecution
- compact
- skill / memory 触发器

它承载的不只是工具调用参数，还包括：

- 当前工具集
- query tracking
- 读文件状态
- dynamic skill 触发
- nested memory 触发
- app state 访问能力

所以代码层真正高耦合的一个根因是：

- 这套系统不是靠“每层只传纯数据”串起来的
- 而是靠一个很重的共享上下文对象贯穿多层

## 10. 当前系统最重的几个耦合点

### 10.1 `tool_result -> compact -> 下一轮上下文`

这是最核心的一条。

工具结果进入历史后：

- 先做 budget
- 再做 microcompact
- 再可能 full compact
- 再被重新拼成下一轮上下文

### 10.2 `SkillTool -> addInvokedSkill -> compact restore`

skill 不是一次性注入文本，而是要跨 compaction 生命周期保活。

### 10.3 `conversationRecovery -> restoreSkillStateFromMessages -> 运行时状态`

resume 不只是恢复 transcript，还要恢复进程内 skill 状态。

### 10.4 `toolExecution -> createAttachmentMessage`

工具执行本身就会直接制造 attachment message，而 attachment 又是上下文系统的一部分。

## 11. 用一句话概括当前架构

如果只用一句话描述当前 repo 的真实结构，不是：

- “模型模块 + 工具模块 + 状态模块”

而更接近：

- “一个以 `query.ts` 为中心、通过 `ToolUseContext` 串起上下文构建、工具执行、compact、恢复和扩展能力的运行时系统”

这也是为什么很多边界在概念上能拆，但在代码运行时仍然会显得很黏。
