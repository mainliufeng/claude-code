# 扩展与集成

这一层负责把仓库从“本地单机会话”扩展成“可接更多外部能力、外部上下文和外部配置”的系统。

它不是主循环本身，但会持续把新能力和新上下文注入主链。

## 2. MCP 为什么会同时影响工具和上下文

MCP 在当前仓库里至少扮演两种角色：

1. MCP tool
   会进入工具池，最终可能进入 API `tools[]`
2. MCP prompt / resource / skill
   会进入 command、skill、attachment 等链路

所以它不是单向影响某一个模块，而是同时打到：

- 工具执行系统
- 上下文构建系统

## 3. 插件与命令为什么是扩展组织层

插件可以贡献：

- commands
- skills
- MCP servers
- 其他辅助能力

而 `commands.ts` 又是很多 prompt command / skill 的统一入口。

所以插件和命令系统做的事情不是“执行某个具体功能”，而是“把扩展能力装配进主系统”。

## 4. IDE / LSP 为什么是上下文扩展

IDE 和 LSP 本身不是工具执行主链，但它们会给当前回合提供非常重要的额外信息，例如：

- 当前活动文件
- 当前选区
- 光标附近代码
- editor 提及
- LSP 初始化状态

这些信息往往会通过 hooks、state、attachments 进入上下文，而不是直接出现在 system prompt。

## 5. 配置与迁移为什么不能忽略

这层决定：

- 默认模型
- 启用哪些 MCP server
- 启用哪些 plugin
- 自动模式、远程控制、权限记忆等开关

同时大量 `migrations` 说明这个产品需要兼顾旧版本用户状态，不能只靠“当前逻辑 if 一下”来解释系统行为。

## 6. 通知与推荐在系统里的作用

通知和推荐不直接参与模型推理，但它们会显著影响用户对系统状态的理解，例如：

- MCP 连接状态
- 模型迁移提醒
- 插件升级提醒
- LSP 初始化提醒
- 能力安装推荐

它们本质上是“运行时状态的人类可读投影”。

## 7. 外部输入为什么也放在这里

语音、浏览器桥接、剪贴板图片、粘贴处理都属于“额外输入源”。

它们的共同特点是：

- 不改变主循环结构
- 但会给主循环输送新的输入材料

## 8. 这一层与其他模块的交互

### 8.1 与主循环与模型调用

- 扩展能力最终都要被装配进一次 turn

### 8.2 与上下文构建、记忆与压缩

- MCP prompt、IDE 信息、外部输入会进入 attachment 和消息

### 8.3 与工具能力、执行与结果回流

- MCP tools 会进入工具池
- 插件也可能影响可用工具和执行能力

### 8.4 与会话与运行时

- 插件、LSP、通知、远程设置等状态都要挂回 AppState 和 REPL

## 9. 一句话总结

这一层真正负责的是：

- 把系统和外部能力、外部上下文、外部配置接起来
- 让主链不是封闭系统，而是可以持续扩展的运行时
